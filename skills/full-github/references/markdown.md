# GitHub Markdown as an active publishing workflow

Official sources checked on 2026-11-15. Apply this to every GitHub text artifact you create or materially change. Choose the richest form that helps the reader act or verify the work. Use the relevant features proactively; do not pad every short comment with every possible syntax. Preserve author content and chronological conversation under [issue-lifecycle.md](issue-lifecycle.md).

## Distinguish syntax from product behavior

The [GFM specification](https://github.github.com/gfm/) defines CommonMark plus tables, task-list items, strikethrough, extended autolinks and restricted HTML. GitHub also sanitizes and post-processes output. Alerts, issue references, mentions, rich previews, math and diagrams depend on the product surface; a generic Markdown parser is insufficient evidence of their behavior. GitHub Docs' Liquid tags and special frontmatter are for its documentation site, not arbitrary repository Markdown.

Before writing, identify the host/version, audience, exact destination and source of truth. README files, issue comments, review comments, Wiki pages, release notes and Project updates do not have identical rendering or interaction. Use explicit links and a plain textual fallback when a richer element is unsupported.

## Select useful formatting every time

| Reader need | Use and verify |
| --- | --- |
| Find and scan information | Hierarchical headings, short paragraphs, meaningful link labels and focused bold emphasis. Use numbered lists for ordered actions and bullets for alternatives. Verify actual heading anchors and relative paths after rename/move. |
| Compare decisions or results | GFM tables with real column headers and alignment where helpful. Escape literal pipes, including pipes inside inline code. Keep cells short; tables do not contain block-level lists or fenced blocks. Link to detailed sections instead. |
| Track small acceptance steps | `- [ ]` and `- [x]` for actual observed work. Keep these distinct from native sub-issues/dependencies and CI results. Retired tasklist blocks are not a setup target. Native children handle independently accepted deliverables. |
| Keep literal text and line structure | Escape punctuation or use code spans. A single newline behaves differently in conversation text and `.md` files; use blank paragraphs or an explicit hard break deliberately. HTML comments hide rendered text but do not protect secrets in source. |
| Add small semantic cues | Consider italic emphasis, `<sub>`/`<sup>`, thematic breaks and familiar emoji where meaningful. HEX/RGB/HSL inline-code color swatches are conversation-specific; retain written color names/values. |
| Share commands, configuration or output | Inline backticks for identifiers and fenced blocks with the actual language (`sh`, `json`, `yaml`, `python`). Use a longer outer fence when documenting fences. Label `diff` blocks for additions/removals; colored output alone does not establish an applied patch. |
| Explain a past statement | A short blockquote plus the exact comment URL. Use `~~strikethrough~~` only when showing a superseded phrase helps; append consequential changed decisions as new comments. |
| Separate primary result from bulky proof | `<details><summary>Descriptive evidence label</summary>` with blank lines around inner Markdown and a closing `</details>`. Keep the result, blockers and required actions visible outside. Expand the disclosure to check its contents. |
| Emphasize a crucial requirement | GitHub alerts `NOTE`, `TIP`, `IMPORTANT`, `WARNING`, `CAUTION`. Use the appropriate meaning, generally one or two per article. Alerts cannot be nested in other elements. |
| Add a side explanation | Footnotes where supported, with unique identifiers and resolvable definitions. Footnotes do not render in Wiki; use ordinary links there. |
| Explain a relationship or process | Mermaid with accompanying prose and meaningful labels. Use real nodes/edges and a supported diagram type; check the host's Mermaid version using an `info` diagram when compatibility is uncertain. |
| Express an actual formula | Inline `$...$` or a fenced `math` block for display math. Define variables and retain readable explanatory text. Check literal currency-dollar escaping and the actual MathJax result. |
| Present real spatial or 3D data | Fenced `geojson`, `topojson` or ASCII `stl`, with valid source data, units/location context and a readable fallback. These are specialist renderers, not a reason to invent map/model data for an unrelated repository. |

Sources: [basic syntax](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax), [tables](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/organizing-information-with-tables), [tasklists](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/about-tasklists), [code fences](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-and-highlighting-code-blocks), [collapsed sections](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/organizing-information-with-collapsed-sections), [diagrams](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams), [math](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/writing-mathematical-expressions).

## Make links and evidence durable

Use repository-relative file/image links in versioned documentation where that keeps branches and forks coherent. Use full destination URLs across the separate Wiki repository. Copy the actual rendered section anchor instead of guessing punctuation or duplicate-heading suffixes. Reference-style links help repeated destinations; custom HTML anchors can preserve an intentional stable target.

Use commit-SHA file/line permalinks for evidence that must survive future edits. A permalink code snippet unfurls only in a comment in its originating repository; another repository receives a link and Markdown files do not embed that snippet. Use ordinary linked code examples in README/Wiki. See [file permalinks](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files) and [snippet behavior](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-a-permanent-link-to-a-code-snippet).

In conversations, native issue/PR/commit references and same-repository label URLs can expose useful titles, state and context. Issue/PR/commit autolink shorthand is not generated in repository files or Wiki; write explicit Markdown links there. External tracker autolinks need actual repository configuration and eligible access. References can generate backlinks. Avoid irrelevant mentions and reference spam; a team/person mention can notify people, including when added by editing a comment. Quote replies are still new chronological issue comments, not nested issue threads. Sources: [autolinks and previews](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/autolinked-references-and-urls), [external autolink setup](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/configuring-autolinks-to-reference-external-resources).

## Images, attachments and accessible presentation

Add meaningful alt text, a caption/context when useful, and textual commands instead of screenshots of commands. Use `<picture>` with light/dark sources and an `<img>` fallback when a diagram or logo needs theme-specific contrast. Check the actual images in both themes. Keep essential meaning out of color alone and avoid large decorative badges. Badges must link to a real current check, version or artifact. See [responsive images](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/quickstart-for-writing-on-github) and [accessible image guidance](https://docs.github.com/en/contributing/style-guide-and-content-model/style-guide#images).

Use actual uploaded evidence or committed assets with known access boundaries. Current GitHub CLI documents `--attach` for issue/PR create, edit and comment, requires push access, and supports image/media uploads. Check installed command help first; the reviewed gh 2.96.0 lacks this flag. On a supported client, local Markdown references are rewritten when the same file is attached; preserve deliberate alt text. Otherwise use the browser upload workflow or a legitimate existing asset URL. Other document attachments use the supported browser flow; do not invent a general REST issue-attachment upload endpoint or use the release-asset API as if it were one.

Files are uploaded immediately in the browser, before comment submission. Public-repository uploads can be public. Inspect sensitive content before upload, then verify the posted destination and intended reader access. A local path pasted into a remote comment does not upload a file. Video playback is codec/browser dependent and needs a textual explanation; CLI video attachments have no alt-text support. Sources: [attachments](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files), [CLI attachments](https://docs.github.com/en/github-cli/github-cli/attaching-files-with-github-cli).

## Use the destination's native behavior

| Destination | Default composition and specific checks |
| --- | --- |
| README / versioned docs | Outcome, quick start, useful navigation, language-tagged examples, meaningful badges and diagram/table where it clarifies the architecture. Verify relative assets at the actual ref. Do not import GitHub Docs Liquid or assume scripts/CSS/iframes survive sanitization. |
| Issue / chronological comment | Reproduction or current result, task acceptance where useful, evidence table, quoted exact earlier comment and collapsible redacted logs. Keep substantive progress in new comments; checkboxes do not replace native type, fields, status or relations. |
| PR description / general comment | Explain changed behavior, linked issue and validation. Use real closing keywords only for intended automatic closure and a table when tests/platform results differ. Put long logs behind a disclosure. |
| PR review | Use line-specific review comments and `suggestion` fences for an exact applicable replacement at the reviewed diff. A suggestion fence in ordinary prose is not a configured review suggestion. Applying suggestions changes commits and may invalidate checks/reviews; revalidate afterward. Batch relevant review comments where it avoids notification churn. |
| Wiki | Use real Home/sidebar/footer/page navigation and links to immutable source when needed. Pull/commit/push the separate Wiki Git repository; verify rendered publication. No footnotes or repository issue shorthand. Math/diagrams have documented support but still require target rendering checks. |
| Release notes | Installation/upgrade, concrete changes, compatibility/limits, verification and real asset/PR links. Preserve existing human prose and immutable published history. Verify the release's renderer before relying on a rich client-side extension. |
| Project README / status update | State actual status, decisions, owners and linked work; tables/checkpoints can summarize progress. Inspect this specific rendered surface before relying on diagrams, alerts or special previews. A Markdown summary does not populate Project field values or saved views. |

Sources: [PR comments and suggestions](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/commenting-on-a-pull-request), [applying suggestions](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/incorporating-feedback-in-your-pull-request), [Wiki editing](https://docs.github.com/en/communities/documenting-your-project-with-wikis/editing-wiki-content).

## Verify publication rather than syntax alone

1. Read existing content and preserve its source of truth. Pick the useful constructs above before writing; do not leave a dense wall of text where a table, diagram, disclosure or checklist serves the reader.
2. Preview Markdown with the destination repository context. The [Markdown REST API](https://docs.github.com/en/rest/markdown) accepts `mode: gfm` and `context: OWNER/REPO`; the raw endpoint has different request/feature behavior. Inspect sanitized HTML, links, table cells and escaped code. Rendering does not publish anything.
3. Publish using the actual file/comment/review/Wiki/release/Project operation with native history and an appropriate linked work context. Read back the exact content, identity and version/commit. Retry uncertain writes only after reconciliation.
4. Inspect the final rendered target in a browser. Open disclosures, follow anchors and asset links, inspect task state, view rich diagrams/math and test theme-dependent content where used. Server-rendered HTML alone does not prove client-side Mermaid, map, STL or MathJax rendering, interactive suggestions, issue-reference previews or notification behavior.
5. Fix material rendering problems at their source. Record the exact URL/ref, checked constructs and any unsupported target behavior. Keep a plain fallback when needed. If browser inspection is unavailable, state which rich rendering remains unverified instead of claiming full visual acceptance.
