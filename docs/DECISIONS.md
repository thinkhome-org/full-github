# Decision history

## 2026-11-15 — Native Codex execution

Full GitHub uses a native skill and existing gh/Git interfaces. GitHub remains the owner of repository, planning, review and publication records. The plugin's discovery and execution helpers expose operation details while preserving host authentication and permissions.

## 2026-11-15 — Complete source and configuration depth

The initial compact endpoint index contained body field hints and could not answer nested configuration questions. Version 0.3 preserves the complete official OpenAPI snapshot and maps every capability to option decisions. Generated schemas are supplemented by explicit errata and current official documentation.

Community discussions inform historical incidents and recovery checks. A workaround is applied only after its relevance to the current host/version is verified. Older forum statements about Projects APIs, concurrency and other changing behavior retain their historical context.

## 2026-11-15 — History and verification

The execution journal appends started/result/verification events in local private state. It excludes payloads, header values and response bodies. A CLI success is recorded separately from read-back evidence and human approval. Interrupted or ambiguous outcomes remain visible and are reconciled before retries.

GitHub's native actor/timeline/audit records remain authoritative for account actions. The local journal is not a tamper-evident audit service. Retention and export decisions follow the organization's actual requirements.

## 2026-11-15 — People and publication

Questions, proposals, defects and code review use their native GitHub conversations. Preserve earlier comments and link accepted proposals into actionable work. Existing single-maintainer policy remains explicit; independent human approvals are requested through actual review controls where required.

Tagged publication uses read-only build permissions and a separate scoped publication job. The release is published after asset-byte verification and provenance generation. Partial drafts resume without overwriting existing assets; incompatible published state fails visibly.

## Open owner decision

Original plugin content awaits a project license choice. Third-party OpenAPI licensing is preserved in NOTICE.md. Account/organization permissions and subscription entitlements are evaluated on the target host without silently broadening access or committing spending.

## 2026-11-15 — Preserve published release identity

Repository release immutability is enabled for future publications. The native GitHub policy freezes published release tags and asset identities and produces release-level verification evidence. Corrections use a new version instead of replacing published bytes. Draft publication remains resumable; existing historical releases retain their recorded original state. This choice implements the project requirement to preserve history.

## 2026-11-15 — Independent review corrections

A fresh three-domain review reproduced gaps in publication identity, source portability, generated Wiki checks and configuration guidance. Release refs now prohibit update/deletion through an active no-bypass repository ruleset. The publisher binds ZIP/source/tag identities before creating or resuming a draft and immediately before publishing. The build job passes its peeled checked-out commit explicitly.

Reviewed release notes accompany generated change history on new drafts. Existing human-written draft prose is preserved and requires review if it originated outside this workflow. Marketplace validation checks portable declared sources, identities and supported policy shape. The generated Wiki catalogs share the same rendering/check gate as repository catalogs.


## 2026-11-15 — Active use and chronological delivery

Issue 14 supersedes the assumption that catalog support and PR history sufficiently demonstrate actual use. Existing work issues had zero comments. New comments are required at material events; existing descriptions retain current scope. Retrospective delivery links are explicitly dated as new comments rather than invented past dialogue. Native sub-issues 15/16 separate deliverables; 16 depends on accepting the gate in 15.

Full setup/audit claims require the complete ledger gate plus live evidence inspection. A gate validates claims and cannot make source evidence truthful or force unloaded skills. Relevant controls must be actively assessed in ordinary tasks. Organization-only fields retain their access boundaries; public Project Priority remains distinct. Missing arbitrary dates, destructive moderation or unrelated personal/billing objects are not reasons to manufacture state.


## 2026-11-15 — Active GFM and GitHub writing

Issue18 extends active-use behavior to content presentation. Markdown rendering alone did not supply an adequate writing workflow. Use a source-backed runbook and ten concrete decisions across files, comments, reviews, Wiki, Project updates and releases. Improve real navigation/comparisons/acceptance/flow/evidence rather than inserting every syntax into every message. Preserve chronology and authorship.

Use the existing native rendering endpoint for HTML preview and the browser for destination-specific behavior, including client-side diagrams/math. Standard GFM and GitHub extensions differ by surface; no generic regex Markdown checker or new parser dependency is introduced. Specialized maps/meshes and equations require relevant content, not a demonstration in every project document.
